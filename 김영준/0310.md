# JPA 복합키 사용을 줄이고 대리키를 사용하는 이유

## 복합키
두 개 이상의 컬럼을 조합하여 기본 키(Primary Key)로 사용하는 것을 의미합니다.

단일 컬럼만으로 유일성을 보장할 수 없을 떄, 여러 개의 컬럼을 조합하여 하나의 레코드를 고유하게 식별하는 방식이다.

예를 들어, 회원 여행 계획(MemberTravelPlan) 테이블에서 travelPlanId(여행 계획 ID)와 memberId(회원 ID)를 함께 사용해 유일성을 보장할 수 있다. 이렇게 하면 같은 회원이 동일한 여행 계획을 중복 등록하는 것을 방지할 수 있다.

하지만, 복합키를 사용할 때 주의해야 할 점이 많다. 단순히 데이터 무결성을 보장하는 장점만 있는 것이 아니라, 설계와 성능 면에서 복잡성이 증가하는 경우가 많다.

 

### 1. JPA를 사용하여 Entity를 생성할때 복잡성이 증가한다.
JPA를 활용하여 복합키를 사용하려면 별도의 복합키 클래스를 정의해야 한다. 이를 위해 @Embeddable, @EqualsAndHashCode 등의 여러 어노테이션을 사용해야 한다.

예제 코드를 보면 확실히 단일 키보다 복잡해 보인다.
```
@Embeddable
@EqualsAndHashCode(onlyExplicitlyIncluded = true)
@Getter
@NoArgsConstructor(access = AccessLevel.PROTECTED)
public class MemberTravelPlanId implements Serializable {

	@Column
	@EqualsAndHashCode.Include
	private Integer travelPlanId;

	@EqualsAndHashCode.Include
	@Column
	private Integer memberId;

	@Builder
	public MemberTravelPlanId(Integer travelPlanId, Integer memberId) {
		this.travelPlanId = travelPlanId;
		this.memberId = memberId;
	}
}
@Entity
public class MemberTravelPlan {
    
    @EmbeddedId
    private MemberTravelPlanId id;
    
    private String travelDetails;

    // 기타 필드 및 메서드
}
```
그리고 이 복합키를 사용하는 엔티티에서도 추가적인 설정이 필요하다.

단순한 @ID 하나만 선언하면 되는 단일 키보다 훨씬 많은 설정이 필요하다.

 

### 2. 인덱스 성능 저하
복합키를 사용하면 여러 컬럼을 조합하여 하나의 키를 만들기 때문에, 인덱스의 성능이 저하될 가능성이 있다.
특히 복합키를 어떤 순서로 구성하느냐에 따라 성능 차이가 발생할 수 있다.

예를 들어, 다음과 같이 travelPlanId와 memberId를 조합하여 복합 인덱스를 생성한다고 가정하자.

CREATE INDEX idx_travel_plan ON MemberTravelPlan (travelPlanId, memberId);
이 경우, 인덱스가 travelPlanId를 우선 검색한 후 memberId를 고려하게 된다.
즉, travelPlanId를 조건으로 검색하는 경우는 최적화되지만, memberId만을 이용한 검색은 인덱스를 제대로 활용하지 못할 가능성이 높다.

복합키의 컬럼 순서에 따라 어떤 쿼리는 빠르게 실행되지만, 어떤 쿼리는 성능이 저하될 수 있다.
이 때문에 설계 단계에서 충분한 고려가 필요하다

### 3. JPA를 통해 쿼리메소드를 작성할때 복잡성 증가
복합키를 사용할 경우, JPA의 findById()를 사용할 수 없고, 복합키 객체를 인자로 전달해야 한다.
즉, 단순히 findById(Long id)를 호출하는 것이 아니라, 다음과 같이 복합키 클래스를 직접 넘겨줘야 한다.
```
public interface MemberTravelPlanRepository extends JpaRepository<MemberTravelPlan, MemberTravelPlanId> {
    Optional<MemberTravelPlan> findById(MemberTravelPlanId id);
}
```

이렇게 되면, 엔티티를 조회할 때도 복합키 객체를 만들어야 하므로 사용성이 떨어진다.

 
```
   MemberTravelPlanEntity findMemberTravelPlanEntityByMember_MemberIdAndTravelPlan_TravelPlanId(Integer memberId, Integer travelPlanId);
   ```
또한, 복합키를 사용하면 복합키 객체 내부의 특정 컬럼을 대상으로 조회해야 하므로 메소드 선언이 길어진다.

즉, 복합키를 사용하면 단순한 조회 쿼리도 길어지고 가독성이 떨어질 수 있다.

 
## 3. 복합키를 사용할 때 고려해야 할 점
복합키는 특정 상황에서는 유용할 수 있지만, 다음과 같은 이유로 신중하게 사용해야 한다.

### JPA에서 관리가 복잡해진다.
별도의 복합키 클래스를 만들어야 하며, 엔티티에서도 @EmbeddedId 또는 @IdClass를 설정해야 한다.
유지보수와 코드 가독성이 떨어질 수 있다.
인덱스 성능 저하 가능성이 있다.
복합키를 어떤 순서로 구성하느냐에 따라 성능 차이가 발생한다.
특정 컬럼을 단독으로 검색할 경우 인덱스를 충분히 활용하지 못할 수도 있다.

### JPA 쿼리 메소드가 복잡해진다.
기본적인 조회 메소드(findById)도 복합키 클래스를 활용해야 하므로 코드가 복잡해진다.
특정 컬럼을 조건으로 조회하는 메소드(findByMemberId 등)도 복합키 객체 내부의 컬럼을 참조해야 하므로, 메소드 선언이 길어지고 가독성이 저하된다
