# JPA에서 Entity 객체에 기본 생성자가 필수인 이유

JPA를 사용할 때 `Entity` 객체에 **기본 생성자**가 반드시 필요하다는 점을 한 번쯤 들어보셨을 겁니다. 그렇다면, 왜 기본 생성자가 필수적일까요? 이번 글에서는 그 이유를 간단히 알아보겠습니다.

---

## 결론: JPA의 내부 동작 방식 때문

JPA는 리플렉션(Reflection)을 사용하여 엔티티 객체를 생성합니다. 이 과정에서 매개변수가 없는 기본 생성자가 반드시 필요합니다.  
그럼 기초부터 천천히 알아가 보겠습니다.

---

## 리플렉션(Reflection)이란?

리플렉션은 구체적인 클래스 타입을 알지 못해도, 그 클래스의 메서드, 타입, 변수 등에 접근할 수 있도록 해주는 **Java API**입니다.  
- 컴파일된 바이트 코드를 통해 **Runtime**에 동적으로 특정 클래스의 정보를 추출할 수 있습니다.

### 예제 코드
```java
@Getter
class Person {
    private String name;
    private int age;

    public Person() {
        this.name = "Unknown";
        this.age = 0;
    }

    public Person(String name, int age) {
        this.name = name;
        this.age = age;
    }

    public void sayHello() {
        System.out.println("Hello, my name is " + name + " and I am " + age + " years old.");
    }
}

public class Main {
    public static void main(String[] args) {
        Object person = new Person();
        // person.getName() // 이 코드는 사용할 수 없다.
    }
}

```
위 코드에서 person은 구체적인 클래스 타입을 알지 못하기 때문에 getName() 메서드를 직접 호출할 수 없습니다. 이런 상황을 해결할 수 있는 기능이 바로 리플렉션입니다.

리플렉션 사용 예제
```
public class Main {
    public static void main(String[] args) throws NoSuchMethodException, InvocationTargetException, IllegalAccessException {
        Object person = new Person();

        // JAVA Reflection
        Class<?> c = Person.class; // 제네릭 타입 지정
        Method getName = c.getMethod("getName"); // getName 메서드 가져오기
        String name = (String) getName.invoke(person); // 메서드 호출 (매개변수 없음)

        System.out.println("name = " + name);
    }
}
```
위 코드에서 보듯이, 리플렉션은 클래스 타입을 알지 못하더라도 메서드나 필드에 동적으로 접근할 수 있도록 도와줍니다.

JPA 역시 리플렉션을 사용해 엔티티 객체를 생성하고 필드에 값을 설정합니다. 여기서 중요한 점은, 리플렉션으로 객체를 생성하려면 기본 생성자가 필수라는 것입니다.

기본 생성자의 접근 지시자가 public 또는 protected만 되는 이유
이유는 Proxy 객체와 연관이 있습니다.

Proxy 객체는 엔티티를 조회할 때 **지연 로딩(Lazy Loading)**을 사용하기 위해 만들어집니다.
지연 로딩을 하면 원본 엔티티를 상속한 Proxy 객체가 반환됩니다.
이때 Proxy 객체는 원본 엔티티를 상속하기 때문에, 접근 지시자가 private이면 에러가 발생합니다.

@NoArgsConstructor(access = AccessLevel.PROTECTED)
우리는 기본 생성자를 사용해 엔티티를 직접 생성하지 않으므로, protected로 선언하여 외부 패키지에서 접근하지 못하도록 제한할 수 있습니다.
이는 JPA 엔티티의 무분별한 생성을 방지하는 데 유용합니다.
지연 로딩(Lazy Loading)이란?
지연 로딩은 JPA에서 필요할 때만 데이터를 가져오는 방식입니다.

예를 들어, A라는 엔티티가 B라는 엔티티를 포함하고 있다고 가정해봅시다:

A를 데이터베이스에서 가져올 때, B가 당장 필요하지 않다면 데이터를 가져오지 않고 **빈 껍데기(Proxy)**만 생성합니다.
B를 실제로 사용할 때, 그때 데이터베이스에서 정보를 가져옵니다.
지연 로딩의 장점
불필요한 데이터 조회를 줄여 성능을 최적화할 수 있습니다.
즉시 로딩(Eager Loading)이란?
즉시 로딩은 지연 로딩과 달리, 당장 필요하지 않더라도 모든 연관된 정보를 즉시 가져오는 방식입니다.

위의 예시에서:

A를 데이터베이스에서 가져올 때, 연관된 B의 정보도 함께 가져옵니다.
B를 사용할 때 이미 A에서 가져왔기 때문에 추가 쿼리를 날릴 필요가 없습니다.
즉시 로딩의 특징
초기 로딩 시간이 길어질 수 있지만, 이후 데이터 접근이 빠릅니다.
