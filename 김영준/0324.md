## 글로벌 트랜잭션 관리
여러개의 개별 트랜잭션이 하나의 작업단위로 묶여 일관성을 유지하며 처리되는걸 글로벌 트랜잭션이라고합니다.
 
만약 Account 서비스에서 잔액 차감은 성공했는데, Payment 서비스에서 잔액 충전 과정에서 문제가 생겼다면? 이전에 처리된 주문 데이터를 롤백해야 하지만, 분리된 데이터베이스 환경이라 단일 데이터베이스처럼 간단히 트랜잭션을 롤백할 수는 없습니다.

 
이 문제를 해결하는 방법으로 대표적으로 2가지 방법이 존재 했습니다.

- Two Phase Commit
- Saga 패턴

### Two Phase Commit
2PC는 작업에 참여하는 모든 시스템에서 트랜잭션을 성공적으로 처리할 수 있는지를 우선 확인한 다음 모드 시스템에서 트랜잭션을 동시에 커밋하거나 롤백할 수 있도록 보장하는 방법이라고 보시면 됩니다. 다음과 같이 동작합니다.
 
트랜잭션 시작 및 ID 발급

애플리케이션이 "분산 트랜잭션 시작해!"라고 하면, 코디네이터라는 리더가 고유한 트랜잭션 ID를 만들어줍니다.


참여자와 싱글-노드 트랜잭션 실행

애플리케이션이 각 노드(참여자)에게 "이 ID로 작업 시작해"라고 말합니다.
노드들은 읽기/쓰기를 하며 자기 작업을 진행합니다.
이 때 문제가 생기면 코디네이터나 노드가 "NO"라 응답합니다.


준비 단계 (Prepare Phase)

작업이 끝나갈 때쯤, 코디네이터가 모든 노드에게 "Prepare"라고 물어봅니다.
노드들은 데이터를 디스크에 저장하고, "문제없어요, 커밋 가능해요!"(Yes)라고 답하거나, "안 돼요!(No)"라고 말합니다.

락을 걸어 다른 트랜잭션이 해당 데이터를 수정하지 못하게 막습니다.




커밋/중단 결정 (Commit Point)

코디네이터가 모든 노드의 답을 듣고 "적용, 취소"를 결정합니다.
이 결정은 디스크에 기록해서 나중에 시스템이 꺼져도 잊지 않게 기록합니다.


결정 전달 및 실행

코디네이터가 "적용" 또는 "취소"라고 노드들에게 말합니다.
전달이 실패하거나 노드가 다운되면, 코디네이터는 성공할 때까지 계속 시도합니다.
"적용" 결정이면 노드가 나중에 깨어나도 무조건 적용되고, "취소"면 모두 롤백이 됩니다.




위의 내용을 읽다보면 몇가지의 문제점이 보이실꺼 같습니다. 저는 이러한 문제점이 보이더군요.
모든 노드가 응답할때까지 코디네이터가 기다려야 하므로 작업의 처리가 길어지겠구나.. 
 
### Saga Pattern
사가 패턴의 주요 개념은 단일 서비스 내에서 Local Transaction을 합니다. 만약 실패하면 사가 패턴은 보상 트랜잭션을 수행하여 이전 로컬 트랜잭션의 변경 내용을 취소하는 방법입니다.
각 로컬 트랜잭션을 끝내고 다음 트랜잭션을 호출하는 메시지, 이벤트를 생성하게 됩니다.
보상 트랜잭션 : 이미 발생한 트랜잭션이 만들어낸 변경을 되돌리기 위해 새로운 트랜잭션을 추가하는 방식
 
Saga 에서 롤백 구현 방식을 역방향 복구와 정방향 복구 2가지의 방법이 존재합니다.
역방향은 이전에 커밋된 트랜잭션을 의미상으로 취소할 수 있는 보상 트랜잭션을 실행, 정방향 복구는 오류가 발생한 지점에서 데이터를 가져와 성공할 때 까지 계속 실행을 시도하는것을 말합니다.
Saga 패턴의 두가지 구현 방식
Saga 패턴의 구현방식은 크게 오케스트레이션 방식 과 코레오그래피 방식으로 나누어집니다.
오케스트레이션
중앙 코디네이터(오케스트레이터)를 사용하여 전체 프로세스의 실행 순서를 정의하고 필요한 보상 조치를 트리거 하는 방식입니다.
이 방식은 중앙 집중형이기에 어떻게 동작하는지 쉽게 파악이 가능합니다. 하지만 중앙 집중이기에 중앙에서 장애가 발생한다면 모든 흐름이 중단되는 단점이 발생합니다.
 
https://learn.microsoft.com/ko-kr/azure/architecture/patterns/saga


코레오그래피
중앙화된 제어 지점없이 여려 협럭 서비스사이에서 이벤트를 교환하며 전체 프로세스를 구성하는 방식입니다.
로컬 트랜잭션이 다른 서비스의 로컬 트랜셕을 트리거하는 도메인 이벤트를 발생시키게 됩니다. 전체 프로세스의 실행에 대한 책임 자체가 각각의 서비스에 분산되기에 단일 시패 지점이 발생하지 않는 장점이 있습니다. 하지만 중앙 집중형이 아니기에 실행순서와 진행상황을 파악하기 어려운 단점이 존재합니다.
 
https://learn.microsoft.com/ko-kr/azure/architecture/patterns/saga
